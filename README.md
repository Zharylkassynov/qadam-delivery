# Qadam Delivery

Учебный MVP доставки. Требования и критерии готовности: [PROJECT_BRIEF.md](PROJECT_BRIEF.md).

## Текущий статус

Реализован сквозной сценарий на локальной PostgreSQL и Supabase Cloud:

- Демонстрационный вход: три клиента и три курьера, роли проверяются сервером.
- Вход Mini App по подписанному Telegram `initData`; новый аккаунт создаётся
  клиентом и сохраняет свои заказы после повторного открытия.
- Заявка «Стать курьером» в профиле Telegram, одобрение/отклонение администратором,
  причина отказа и повторная подача. Одобренный пользователь получает кабинет курьера.
- Клиент заполняет доставку, проверяет данные на отдельном экране и создаёт
  заказ с адресами, получателем, телефоном и сведениями о посылке.
- Курьер видит доступные заказы, принимает заказ и последовательно отмечает
  получение груза, начало доставки и завершение.
- Статусы обновляются у клиента опросом сервера каждые 3 секунды.
- Карта с подтверждёнными клиентом точками А/Б и последней позицией курьера;
  время измерения/получения, точность и предупреждение через 90 секунд без новых данных.
- Поиск улицы и дома по Алматы и окрестностям через Geoapify. Один найденный
  дом показывается автоматически; неоднозначный адрес требует выбора результата.
  Подложка Positron с чёткими тайлами @2x и маркерами Qadam.
- Заказы, история событий и сессии сохраняются в PostgreSQL. Повторное открытие
  страницы восстанавливает данные с сервера.
- Клиент может отменить заказ до назначения курьера. Завершённые и отменённые
  заказы доступны в истории.

Публичное учебное демо: **https://qadam-delivery.vercel.app**.
Приложение опубликовано на Vercel 19 октября 2026 и работает с Supabase Cloud.
Для открытия ссылки локальный сервер и Docker не нужны.

Реализован администратор заявок курьеров. Пока не реализованы: роль бизнеса,
полный диспетчерский раздел администратора и дорожные маршруты.
Обычный браузерный вход сохраняется рядом с Telegram-входом.
Город демонстрации — Алматы; геофильтрации заказов пока нет. Название и часовой
пояс заданы в `src/lib/service-area.ts`, сохранённые адреса не переписываются.

Стек: Next.js 16, React 19, TypeScript, Tailwind CSS, Node.js, `pg`, SQL-миграции.
Точные версии зависимостей зафиксированы в `package-lock.json`.

## Карта и геопозиция: проверка в Telegram

1. Клиент: в новом заказе введите улицу и дом → «Найти отправление на карте».
   Один найденный дом появится на карте автоматически. Если результатов несколько,
   выберите нужный. Проверьте вход → «Выбрать этот адрес». Повторите для доставки.
   При результате «Только улица» точку дома нужно уточнить вручную.
   Если поиск недоступен, нажмите «Указать вручную на карте». Изменение текста
   адреса в форме сбрасывает его точку, чтобы не сохранить координаты другого места.
2. Подтвердите заказ. В деталях видны А и Б; их координаты сохранены в PostgreSQL.
   Без выбора точек заказ тоже работает, но соответствующие адреса на карте не появятся.
   Старым заказам не приписываются выдуманные координаты.
3. Назначенный курьер: примите заказ → «Передавать геопозицию» → разрешите доступ
   Telegram/устройству. Telegram 8.0+ использует LocationManager; браузер —
   Geolocation API (HTTPS или localhost). На компьютере точность может быть низкой.
4. Клиент: дождитесь появления К и времени последней точки. Обновление заказа —
   каждые 3 секунды; курьер запрашивает новую позицию примерно раз в 15 секунд.
5. Курьер: сверните Mini App или выйдите из деталей заказа. Передача остановится.
   После возвращения включите её кнопкой снова. Через 90 секунд без измерения
   клиент увидит предупреждение об устаревшей позиции; фонового трекинга нет.
6. Откажите в GPS: статусы и завершение доставки должны работать. Завершите заказ,
   переоткройте его в истории: А/Б и последняя точка сохраняются, новая геопозиция
   для завершённого заказа сервером не принимается.

Карта: Leaflet 1.9.4, Geoapify Positron, тайлы @2x. Поиск выполняется кнопкой,
не на каждое нажатие клавиши; выдача ограничена Алматы и окрестностями.
Geoapify получает только поисковый текст или номера тайлов, без получателя,
телефона, идентификатора заказа и токена Telegram. `GEOAPIFY_API_KEY` хранится
на сервере: в локальном `.env.local` и защищённом Vercel Production. Не используйте
префикс `NEXT_PUBLIC_`. Preview не принимает этот ключ.

Для новой копии проекта возьмите ключ своего Geoapify-проекта и добавьте в
игнорируемый `.env.local`: `GEOAPIFY_API_KEY=ваш_ключ`. Затем обычный `npm run dev`.
Без ключа поиск покажет ручной fallback, карта использует стандартный OSM.
Для него соблюдайте [политику тайлов OSM](https://operations.osmfoundation.org/policies/tiles/).
Публичный Nominatim не используется. Офлайн-загрузки и массовой предзагрузки нет.

`/api/geocoding`, `/api/map-config` и `/api/map-tiles/[z]/[x]/[y]` требуют сессию.
Тайлы загружаются через серверный обработчик с bearer/cookie; это работает и при
запрете сторонних cookie в Telegram Web. Браузер и сервер кэшируют карту сутки.
Источник Geoapify, OpenMapTiles и OpenStreetMap указан на карте.
Лимиты в `qadam.service_limits` общие для всех серверных экземпляров: максимум
1000 поисков и 6000 запросов тайлов в сутки, плюс ограничения частоты/пользователя.
Это до 2500 кредитов Geoapify в сутки при цене 1 за поиск и 0,25 за тайл
([тариф и расчёт кредитов](https://www.geoapify.com/pricing/));
контролируйте также использование ключа вне приложения в кабинете поставщика.
При лимите или ошибке сервис не блокирует создание и завершение доставки.
Карта не строит дорожный маршрут/ETA; внешняя навигация открывается отдельной ссылкой.

Автотесты используют подменённые тайлы и явно симулированные GPS/Telegram LocationManager;
реальную выдачу разрешения в Telegram на телефоне проверьте по шагам выше.

## Публикация на Vercel

Этап 1: подготовлены `vercel.json`, настройки Node.js 22.x, TLS-файлы в
API-сборке, управление соединениями Vercel Functions и проверка переменных
окружения. Production требует HTTPS и Supabase transaction pooler с ролью
`qadam_app`; Preview пока работает без входа и подключения к базе.
Этап 2: выполнена Production-публикация на Vercel, настроен точный HTTPS-origin,
подключена существующая Supabase Cloud. `DATABASE_URL` хранится как секрет
только Production. Функции работают во Frankfurt (`fra1`), Node.js — 22.x.
Приватный GitHub-репозиторий подключён для автоматической публикации `main`.

По публичному адресу прошли 6 браузерных сценариев: доставка клиентом и курьером,
повторный вход и история, проверки авторизации и Secure-cookie, мобильные ширины
360/390 px, повтор создания после потери ответа и восстановление после сетевой ошибки.
Проверка алиаса localhost применяется только к локальному запуску и в HTTPS-наборе
пропускается. Проверочный заказ QD-0011 доставлен и восстановлен из облачной истории.

Для повторения проверки установите `E2E_ORIGIN=https://qadam-delivery.vercel.app`
и выполните `npm run test:deployed`. Тесты создают помеченные E2E-заказы, не удаляя данные.

Полные настройки, переменные и порядок публикации:
[docs/VERCEL_DEPLOYMENT.md](docs/VERCEL_DEPLOYMENT.md).
`.env.vercel.example` содержит только шаблон без секретов.
GitHub Actions проверяет типы, серверные тесты, сборку и браузерный сценарий
на отдельной временной PostgreSQL. Облачные пароли для CI не нужны.

Проверка соединения и сценария через transaction pooler без изменения `.env.supabase`:

```powershell
npm run db:cloud:transaction:check
npm run test:cloud:transaction
```

После сборки `npm run check:build` проверяет включение TLS-сертификата в
каждый серверный API-бандл. Локальные `.env`, артефакты тестов, конфигурации
IDE и личные инструкции инструментов исключены из Git и загрузки Vercel.

## Утверждённый дизайн

[Qadam Delivery — MVP Design в Figma](https://www.figma.com/design/syjrAMIWnlfshbnqmknsL2).
В приложение перенесены действующие сценарии клиента и курьера:
главная, оформление и проверка заказа, детали и статусы доставки, история,
профиль, вход, загрузка, пустой список и сетевые ошибки.

Основные элементы вынесены в `src/components/delivery-ui.tsx`, форма и
подтверждение — в `order-form.tsx`, экраны — в `delivery-workspace.tsx`.
Существующие запросы, сессии, опрос сервера и защита от повторного создания
сохранены в `delivery-app.tsx`. Серверная схема и API не изменены.
Тип и описание посылки сохраняются в существующем поле комментария.

Цвета, отступы и адаптивные стили: `src/app/globals.css`. Мобильные ширины
390 и 360 px проверяются в Chrome; длинный контент прокручивается внутри
экрана, основная кнопка остаётся видимой. Настольная версия использует
боковую навигацию. Иконки экспортированы из утверждённой Figma и сохранены
в `public/icons`. Шрифт Onest обслуживается локально из `public/fonts`,
лицензия OFL сохранена рядом; загрузка шрифта с Google при сборке не нужна.

Данные в интерфейсе берутся из базы. Числа, имена и стоимость из макета не
подставляются в реальные заказы. Стоимость — по согласованию. В приложении
нет демонстрационной кнопки завершения заказа от имени клиента: завершить
доставку может только назначенный курьер. Геолокация явно показана как
недоступная; вместо вымышленных точек предложена внешняя навигация по адресам.
Экраны бизнеса и администратора остаются в Figma до реализации их ролей/API.

## Supabase Cloud

Создан отдельный проект **Qadam Delivery** в регионе Frankfurt (`eu-central-1`):
https://supabase.com/dashboard/project/ibuuibvkbiuaqrqobitk

Облачная схема и шесть демоаккаунтов подготовлены через подключение Supabase.
Соединение с облаком настроено через Session pooler с проверкой TLS-сертификата.
Локальная база и локальные заказы не переносились и не заменялись.

Конфигурации разделены:

| Режим | Настройки | Запуск |
| --- | --- | --- |
| Локальная разработка, Docker | `.env` | `npm run dev` |
| Приложение с Supabase Cloud | `.env.supabase` | `npm run dev:cloud` |

`.env.supabase` содержит сгенерированный пароль ограниченной роли `qadam_app`;
файл исключён из Git. Шаблон без секретов: `.env.supabase.example`.
Не заменяйте его паролем администратора `postgres`.
Для IPv4 выберите в Supabase **Connect → Direct → Session pooler** и скопируйте
точный хост. Порт — `5432`, имя пользователя — `qadam_app.<project-ref>`,
база — `postgres`. Точный хост нельзя угадывать по региону.

Настроенный хост: `aws-1-eu-central-1.pooler.supabase.com:5432`.
Облачное соединение использует TLS с проверкой сертификата. Публичный CA,
полученный по ссылке **Database → Settings → Download certificate**, сохранён
в `config/certs/supabase-root.crt`; путь задан в `DATABASE_SSL_CA_FILE`.
SHA-256 файла: `700723581420dd1ac98fd7e9ac529f0ef210eadcaf87fc868a3ad7d114c2f3b7`.
Проверка `db:cloud:check` подтверждает TLS именно клиентского сокета:
`pg_stat_ssl` за пулером отражает другое соединение между пулером и PostgreSQL.
Отключение проверки сертификата не поддерживается. Пул ограничен тремя
соединениями по умолчанию (`DATABASE_POOL_MAX`). Это конфигурация постоянного
Node.js-сервера. Для Vercel подготовлен отдельный профиль на transaction
pooler `6543` с тем же ограниченным пользователем и проверкой TLS.

Проверка настроенного подключения и запуск:

```powershell
npm run db:cloud:check
npm run dev:cloud
```

Облачная версия настроена на отдельный адрес **http://127.0.0.1:3001**.
Команды `dev:cloud` и `start:cloud` берут порт из
`APP_ORIGIN` в `.env.supabase` (сейчас 3001). Локальная версия на порту 3000
может работать одновременно. Конфигурации сборки также разделены:
`.next` и `.next-cloud`.
Для производственного режима облачной конфигурации:

```powershell
npm run build:cloud
npm run start:cloud
```

Для проверки того же сценария на облаке:

```powershell
npm run test:cloud:e2e
```

Команда запускает отдельный сервер на порту 3200 с облачной базой и выполняет
тот же набор браузерных сценариев, что и локальный тест. Она создаёт явно
помеченные `E2E` заказы в облаке и **не удаляет** данные. Результаты — в
`test-results-cloud`. Облачные миграции и демоаккаунты должны быть подготовлены
заранее административным подключением; тест и приложение используют только
ограниченную роль.

Проверено 18 октября 2026: облачное соединение под `qadam_app` использует
TLS 1.3 с проверкой сертификата; после переноса дизайна прошли все 6 облачных браузерных тестов.
В облачной PostgreSQL сохранён проверочный заказ №1 со статусом DELIVERED,
клиентом 1, курьером 1 и шестью последовательными событиями. Его история
восстанавливается после закрытия страницы и нового входа. Заказ явно помечен
как автоматическая проверка. Локально повторно прошли 15 серверных проверок
(включая настройки TLS) и 6 браузерных сценариев; облачная сборка успешна.
Собранная облачная версия отдельно запущена на порту 3001: через браузер
проверены вход клиента и сохранённая история заказа №1.

У `qadam_app` нет прав изменения схемы, ролей или существующих пользователей.
Для Telegram разрешена вставка только email, имени и хеша недоступного случайного
пароля; роль нового пользователя задаётся значением CUSTOMER по умолчанию в БД.
Приложение читает пользователей, работает с заказами, событиями, сессиями и счётчиком
попыток входа. Таблицы `qadam` закрыты для `PUBLIC`, `anon`, `authenticated`
и `service_role`. Метаданные миграций защищены RLS без пользовательских
политик: их читает только владелец/администратор.

Файлы `db/migrations` остаются источником схемы. Миграции облака применены
через Supabase с теми же контрольными суммами в `public.qadam_migrations`.
Пароль `qadam_app` создан локально; в SQL настройки роли передан только
SCRAM-SHA-256 verifier. При первоначальной настройке нового проекта помощник
использует `scripts/export-supabase.ts`, который не публикует открытый пароль.
Повторно применять начальную настройку к существующему проекту не нужно.

## Telegram Mini App

Бот учебной демонстрации — [@qadam_delivery_bot](https://t.me/qadam_delivery_bot).
Меню бота открывает тот же публичный HTTPS-сайт. Подключение и воспроизводимый
сценарий проверки: [docs/TELEGRAM_MINI_APP.md](docs/TELEGRAM_MINI_APP.md).

Сервер проверяет HMAC подпись исходного `initData`, срок 1 час и идентификатор
пользователя. Telegram username и переданный клиентом выбор роли не дают прав.
Новые пользователи — клиенты. В профиле можно подать заявку курьера.
Администратор рассматривает её в том же Mini App; результат и доступ к заказам
обновляются опросом сервера. После повторного открытия решение сохраняется.
Связывание с общими демоаккаунтами по имени или email не выполняется.

Сессия Mini App передаётся через Bearer-заголовок и хранится только в памяти
страницы. Это позволяет работать в Telegram Web без сторонних cookie.
После повторного открытия Telegram заново подтверждает тот же аккаунт; заказы
читаются из БД. Обычный демовход продолжает использовать HttpOnly-cookie.

Проверено автоматически 19 октября: 31 серверная проверка, сборка и браузерные
сценарии доставки и заявок. Три Telegram-сценария используют синтетический ключ и
подменённый SDK только в отдельной локальной тестовой БД. Они не заменяют
ручную проверку настоящего запуска в Telegram. Облачная проверка ограниченной
роли подтвердила создание клиента и запрет назначения роли; временные данные
проверки откатились транзакцией.

Заявки хранятся в `qadam.courier_applications`, отдельное право администратора —
в `qadam.administrators`. Runtime читает состав администраторов, но не меняет его.
Первый администратор назначен владельцем БД на подтверждённый Telegram-аккаунт
создателя QD-0018. Его роль клиента и доступ к своим заказам сохранены.
Права курьера вычисляются из одобренной заявки; право UPDATE пользователей
приложению не выдаётся. Окончательное решение не перезаписывается, отклонённая
заявка остаётся в истории после повторной подачи.

Утверждённые экраны: [Figma — заявки курьеров](https://www.figma.com/design/syjrAMIWnlfshbnqmknsL2?node-id=43-1290).

## Запуск приложения

Требования: Node.js 22.14+ (поддерживаемая LTS-версия), npm, Docker Desktop.

1. В новой копии проекта скопируйте `.env.example` в `.env`. Замените
   `replace_with_a_random_password` одинаковым случайным паролем во всех трёх
   строках: `POSTGRES_PASSWORD`, `DATABASE_URL`, `TEST_DATABASE_URL`.
   В текущем рабочем каталоге `.env` уже настроен.
2. Выполните:

```powershell
docker compose up -d --wait
npm ci
npm run db:migrate
npm run db:seed
npm run dev
```

Откройте http://127.0.0.1:3000 или http://localhost:3000. Если `APP_ORIGIN`
указывает на `127.0.0.1` или `localhost`, разрешены оба имени с тем же протоколом
и портом. Сессии у этих адресов отдельные. Остальные источники запросов сервер
отклоняет. Для другого порта измените
`APP_ORIGIN` и запустите, например, `npm run dev -- --port 3001`.

Демонстрационные аккаунты:

| Роль | Логины |
| --- | --- |
| Клиент | `customer1@qadam.demo`, `customer2@qadam.demo`, `customer3@qadam.demo` |
| Курьер | `courier1@qadam.demo`, `courier2@qadam.demo`, `courier3@qadam.demo` |

Начальный пароль для всех шести аккаунтов: **`QadamDemo-2026!`**.
Это специально опубликованный пароль учебной демонстрации. Фактический пароль
задаётся в `DEMO_PASSWORD` в `.env`; после изменения выполните `npm run db:seed`.
Сидирование не удаляет заказы и не меняет роли существующих пользователей.
Не используйте реальные пароли участников. Демовход включается только при
`DEMO_AUTH_ENABLED=true`; для отключения установите `false` и перезапустите сервер.

Проверка производственного режима:

```powershell
npm run build
npm start
```

Сначала остановите dev-сервер на порту 3000 сочетанием Ctrl+C.

## Проверки

Автоматические тесты используют отдельную БД `qadam_delivery_test`, заданную
в `TEST_DATABASE_URL`. Они отказываются работать с именем базы без суффикса
`_test`; демонстрационная база приложения не используется. Локально создайте
тестовую БД командой ниже (безопасно повторять):

```powershell
npm run db:test:setup
npm run typecheck
npm test
npm run test:e2e
npm run build
```

Интеграционные тесты применяют миграции и проверяют авторизацию, изоляцию
аккаунтов, конкуренцию двух курьеров, последовательность статусов,
идемпотентность, отмену и восстановление данных после переподключения.
Браузерные тесты требуют установленный Google Chrome, сами готовят тестовые
аккаунты и запускают отдельный сервер на порту 3100. Проверяют доставку в двух
независимых браузерных сессиях, обновление статусов, повторное открытие/вход,
историю, HTTP API и мобильные ширины 390/360 px. Дополнительно проверяют
возврат из подтверждения с сохранением полей, ошибки валидации, загрузку,
пустой список, восстановление соединения и повтор создания после потери
ответа сервера без дублирования заказа. Браузерные тестовые заказы
помечены `E2E` и остаются только в тестовой БД.

Результат проверки интерфейса 18 октября 2026: TypeScript, локальная и облачная
производственные сборки успешны; прошли 15 серверных проверок, 6 локальных
и 6 облачных браузерных тестов. В собранной версии
дополнительно проверены HTTP 200, вход, чтение заказов из БД, выход и отказ
в доступе по отозванной сессии. Мобильный и настольный интерфейсы просмотрены
по снимкам экрана из браузерных тестов.

Ручная проверка:

1. Откройте http://127.0.0.1:3000 в обычном окне и войдите клиентом 1.
2. В другом профиле браузера или приватном окне войдите курьером 1.
   Разные вкладки одного профиля делят cookie и не подходят для двух аккаунтов.
3. Клиент: «Заказать доставку» → заполните адреса, имя, телефон и данные посылки
   → «Проверить заказ». Проверьте данные и нажмите «Подтвердить заказ».
   Кнопка «Изменить данные» возвращает в заполненную форму.
4. Курьер: дождитесь появления заказа, выберите его → «Принять заказ».
5. Клиент: в течение примерно 3 секунд статус станет «Курьер назначен».
6. Курьер: «Посылка у меня» → «Начать доставку» →
   «Завершить доставку». На каждом шаге проверьте статус в окне клиента.
7. Закройте окно клиента, откройте снова → «Мои заказы» / «Заказы» → «Завершённые».
   Должен быть виден
   доставленный заказ с курьером и шестью событиями.
8. Выйдите и войдите снова: заказ остаётся в истории.
9. Дополнительно войдите курьером 2 в третьем профиле. Он не должен видеть
   заказ, уже назначенный курьеру 1. Новый свободный заказ можно попробовать
   принять одновременно двумя курьерами: успешно назначится только один.
10. Остановите приложение и контейнер (`docker compose stop`), затем запустите
    их снова. Заказы и история должны сохраниться.

Отсутствие доступа к БД или серверу показывается как ошибка обновления.
Старые данные не выдаются за успешно обновлённые. Клиентская форма сохраняет
ключ запроса при повторе после сетевой ошибки, чтобы не создать дубликат.

## Сервер и база

- Миграции: `db/migrations`. Повторное применение безопасно; изменение уже
  применённого файла обнаруживается по контрольной сумме. Добавляйте новые
  миграции вместо редактирования применённых.
- Таблицы находятся в схеме `qadam`, отдельно от `public`. Это упрощает
  дальнейшее подключение Supabase без публикации таблиц через Data API.
- Пароли хешируются scrypt; в БД хранится SHA-256-хеш случайного токена сессии.
  Cookie — HttpOnly, SameSite=Lax, Secure при HTTPS. Срок сессии — 7 дней;
  выход удаляет сессию на сервере.
- Сервер берёт пользователя и роль из сессии. Клиент не назначает себе роль,
  идентификатор клиента или курьера.
- Создание заказа и события фиксируются в транзакции. Принятие и смена статуса
  блокируют строку заказа через `SELECT ... FOR UPDATE`. Повтор того же
  действия не создаёт второе событие.
- Заказ создаётся с событиями CREATED → SEARCHING_FOR_COURIER в одной
  транзакции. Далее ACCEPTED → PICKED_UP → IN_TRANSIT → DELIVERED.
  Отмена клиентом разрешена только до назначения курьера.
- Адреса вводятся текстом; поиск находит точки А/Б, клиент подтверждает их на карте.
  Координаты и последняя позиция назначенного курьера сохраняются на сервере.
  Дорожный маршрут и ETA в этой версии не рассчитываются.
- Для локальной разработки используется владелец Docker-БД. В Supabase
  приложение использует отдельную ограниченную роль. Публичный HTTPS-хостинг
  приложения — Vercel; исходники находятся в приватном GitHub-репозитории.

## Локальная база данных

Требования: Docker Desktop с работающим Linux Engine и Docker Compose.

Для текущего рабочего каталога `.env` уже создан с отдельным случайным паролем.
Для новой копии проекта скопируйте `.env.example` в `.env`, замените пароль
и укажите тот же пароль в `DATABASE_URL`. Не публикуйте `.env`.

Запуск и проверка:

```powershell
docker compose up -d --wait
docker compose ps
docker compose exec -T db psql -U qadam -d qadam_delivery -c "SELECT current_database(), version();"
```

База доступна только на этом компьютере: `127.0.0.1:55432`.
Строка подключения находится в `.env`. Порт в `DATABASE_URL` должен совпадать
с `POSTGRES_HOST_PORT`. Данные находятся в отдельном Docker-томе
`qadam-delivery_postgres_data` и сохраняются при остановке контейнера.
Изменение пароля в `.env` не меняет пароль уже созданной базы.

Остановка и повторный запуск:

```powershell
docker compose stop
docker compose up -d --wait
```

Не используйте `docker compose down -v`, если данные нужно сохранить.
Локальная база предназначена для разработки и резервного показа.
Браузерная HTTPS-версия доступна на Vercel; подключение Telegram Mini App
выполняется отдельным этапом.

## Smart Inventory

Контейнеры проекта `smart-inventory` остановлены по запросу владельца.
Их данные, тома и контейнеры сохранены. Вернуть ранее активные контейнеры
можно через Docker Desktop, запустив их индивидуально, либо штатной командой
запуска Supabase из каталога Smart Inventory. Контейнер edge-runtime уже был
остановлен до этих действий.

Инфраструктура Qadam использует отдельный Compose-проект, том и порт.
