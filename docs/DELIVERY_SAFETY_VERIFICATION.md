## Новые проверки

- Принятие заявки издалека остаётся разрешённым при выполненной готовности курьера.
- Удалённые забор и вручение отклоняются через новый и старые API; прямое
  обновление статуса, имитирующее старый сервер, также блокирует база.
- Проверены отсутствие точек, устаревшие/будущие координаты, неточная позиция,
  отсутствие погрешности, фиксированный радиус, отключение смены и согласия,
  блокировка курьера и источник Telegram.
- Два разных шестизначных кода: права чтения, обязательность, сроки,
  сохранение неверных попыток, пять попыток, ограничение перевыпуска.
- Повтор успешного/ошибочного запроса и одновременные копии не создают
  повторное доказательство и не тратят попытку повторно.
- Отказ до забора, смена курьера до/после забора и изменение точки
  аннулируют прежние коды/запросы. Курьер не перемещает адрес.
- Старый заказ без точки восстанавливает владелец. Старые заказы в пути
  учитываются при включении, без выдуманного доказательства забора.
  Прежний `PICKED_UP` продолжает работу в `IN_TRANSIT`, включая фото.
  Включение отдельно проверяется одновременно со старым запросом, удерживающим
  строку заказа: он заканчивается до учёта старых доставок. Для этого используется
  `EXCLUSIVE` ([совместимость блокировок PostgreSQL 17](https://www.postgresql.org/docs/17/explicit-locking.html)).
- Проверены сессия, источник запроса, роль и строгий формат API.
  Обычные ответы, публичное отслеживание и история запросов кодов не раскрывают.
- Обязательное фото сохраняется как условие вручения. Изменение адреса
  во время загрузки не воскрешает прежнее фото; нужен новый снимок.

Отдельно устранены: ранний переход к карте до получения условий заказа
и нестабильность прежнего теста лимитов на границе календарной минуты.
Вторая правка фиксирует часы внутри теста, правило ограничения запросов не меняет.

## Supabase

Три миграции применены одной операцией `verified_delivery_handoffs`.
Контрольные суммы в `public.qadam_migrations` сверены с локальными файлами:

| Файл | SHA-256 |
| --- | --- |
| `20261110121546_verified_handoffs.sql` | `262595dc9e6cebb9fb7db1d1b4ba90804b4506a91d9c2fc77af5a0ffcfd422da` |
| `20261110124535_handoff_status_guard.sql` | `abcac7e41a34e75f4b453f3dc11760aef14e16ba842d26700bcbdd03a55dc58b` |
| `20261110125043_handoff_activation.sql` | `07adea3dc8c81c71fcb00962f19ce13c47529a4441abe28fc261db551b15d23c` |

RLS включён на трёх новых таблицах. У `anon`, `authenticated`, `service_role`
нет чтения кодов. `qadam_app` может читать и обновлять коды, добавлять доказательства,
но не изменять их; включение доступно один раз и не может быть отменено этой ролью.
Проверены политики и наличие триггера. `activated_at` в Production пока `NULL`:
включение произойдёт после публикации новой версии, первым авторизованным запросом.
Действующий сервер и реальные заказы для проверки не подменялись.

После установки новых замечаний security advisor нет. Сохраняется прежний
информационный пункт о закрытом журнале `public.qadam_migrations` без публичной
политики ([пояснение Supabase](https://supabase.com/docs/guides/database/database-linter?lint=0008_rls_enabled_no_policy)).
До изменения также отмечались три прежних внешних ключа без индекса
([пояснение](https://supabase.com/docs/guides/database/database-linter?lint=0001_unindexed_foreign_keys));
их изменение не требуется для новых таблиц и этой доработки.
Метаданные Vercel подтверждают наличие серверного ключа кодов в Production;
значения секретов не читались и не выводились.
