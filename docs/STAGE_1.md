## Публикация и проверка

Если при создании заказа или смене статуса возникает «Сервер временно недоступен»,
сначала выполнить раздел об ошибке `42501` ниже.

1. В WebStorm проверить изменения, закоммитить и отправить ветку. Создать Pull Request в `main`.
2. В Vercel → Settings → Environment Variables → Production задать
   `DEMO_AUTH_ENABLED=false`. Дождаться зелёного CI и смёржить PR.
   Убедиться, что Production опубликован с этим значением; при необходимости выполнить Redeploy.
3. В Supabase → SQL Editor выполнить весь файл
   [sql/stage-1-disable-demo.sql](sql/stage-1-disable-demo.sql).
   Он отменит открытые заказы демо-клиентов, добавит события отмены и отключит
   демо-аккаунты. Их существующие сессии сразу перестанут давать доступ.
   История сохраняется. Повторное выполнение не создаёт повторных событий отмены.
   Это очистка данных, а не миграция: запись в `public.qadam_migrations` не нужна.
4. Просмотреть результат последнего SELECT в SQL: открытые заказы реальных аккаунтов
   не изменяются автоматически. Проверить, нет ли среди них старых пробных доставок.

## Проверка после публикации

1. Открыть сайт в обычном браузере: видны заголовок «Откройте Qadam в Telegram»
   и ссылка на `@qadam_delivery_bot`; формы логина и пароля нет.
2. Открыть Mini App через Telegram: вход автоматический. На главной и в профиле
   клиента и курьера нет учебных подписей и кнопок выхода.
3. Создать заказ клиентом. До принятия курьер видит адреса и подсказку о контактах,
   но не имя и телефон получателя. После принятия видны имя и кнопка звонка.
4. Администратор видит контакты свободного заказа в разделе «Все заказы».
5. Закрыть и открыть Mini App: заказ и текущий статус сохранены.

## Исправление ошибки 42501 в опубликованной версии

26.10.2026 Vercel зафиксировал `Request failed: 42501` для `POST /api/orders`
и смены статуса заказа. В Supabase у `qadam.order_events` включён RLS,
но нет политик доступа. Поэтому сервер не может записать событие, транзакция
создания или смены статуса откатывается; чтение истории также ограничено.

Владелец выполняет в Supabase → SQL Editor весь файл
[sql/stage-1-fix-order-events.sql](sql/stage-1-fix-order-events.sql).
Он создаёт политики SELECT и INSERT только для `qadam_app`, сохраняет RLS,
закрывает публичные API-роли и записывает SHA-256 миграции в `public.qadam_migrations`.
Редактирование и удаление истории приложению не разрешаются. Данные не удаляются.
Повторный запуск SQL допустим. Перезапуск Vercel для изменения прав БД не нужен.

После выполнения закрыть и открыть Mini App, повторить создание заказа или смену
статуса и убедиться, что история отображается. Затем сообщить результат ассистенту,
чтобы он проверил политики и новые журналы. Это исправление SQL выполнил владелец;
для следующих согласованных задач он разрешил ассистенту выполнять SQL самостоятельно.

Регрессионный тест создаёт временную ограниченную роль в локальной тестовой БД,
проверяет чтение, добавление события, запрет UPDATE/DELETE и повторное применение
миграции. Все временные права и данные откатываются транзакцией.

После исправления локально успешно выполнены все пять обязательных команд:
`npm run typecheck`, `npm test` (52 проверки), `npm run build`,
`npm run check:build` (17 API-бандлов), `npm run test:e2e` (25 сценариев).
Облачное исправление подтверждено 26.10.2026: checksum совпадает с файлом миграции,
политики SELECT/INSERT действуют только для `qadam_app`, UPDATE/DELETE запрещены.
Активных демо-аккаунтов и открытых заказов демо-клиентов нет. Владелец подтвердил,
что приложение работает в Telegram; новых ошибок Vercel за последние пять минут проверки нет.
Файлы исправления и документацию владелец добавляет в Git и отправляет через GitHub вручную.
