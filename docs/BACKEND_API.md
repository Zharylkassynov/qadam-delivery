# Самостоятельный бэкенд: локальная проверка

Дата: 27.10.2026. Ветка: `stage-2-backend-api`. План утверждён владельцем.

## Результат и границы

Целевая схема: интерфейс на Vercel, собственный API и PostgreSQL на PS.kz.
Этот этап готовит и проверяет её локально. Аренда, переключение Production,
перенос облачных данных и настройка настоящего вебхука в него не входят.

- `frontend/` — отдельное приложение Next.js с главной страницей, правилами и
  политикой. Оно переиспользует существующие экраны и стили из `src/`. API-маршрутов
  у него нет. Запросы браузера идут непосредственно на отдельный API.
- `backend/` — отдельное приложение Next.js только для API и `/health`. Его
  маршруты переиспользуют существующие обработчики из `src/app/api/` и логику
  `src/lib/`. Правила доступа, транзакции, лимиты тела запроса и приватность контактов
  сохраняются. Дублировать бизнес-логику в обёртках маршрутов не нужно.
- Исходное приложение из корня сохранено для действующего размещения. Пока
  Production работает по прежней схеме Vercel + Supabase.
- Новые таблицы и SQL-миграции на этом этапе не нужны.

## Проверка на компьютере

Запустить Docker Desktop с Linux-контейнерами, затем:

```powershell
npm run docker:up
npm run docker:check
npm run docker:status
```

Адреса:

| Сервис | Адрес | Назначение |
| --- | --- | --- |
| Интерфейс | http://127.0.0.1:3200 | Обычный локальный вход и интерфейс доставки |
| API | http://127.0.0.1:3210 | Вход, заказы, статусы, карта, бот |
| Готовность API | http://127.0.0.1:3210/health | Проверяет подключение к PostgreSQL |
| PostgreSQL | `db:5432` внутри Docker | Порт на компьютер и в интернет не опубликован |

`http://127.0.0.1:3200/api/session` должен возвращать 404: это проверяет, что
интерфейс больше не выполняет запросы к БД сам.

Используется прежний отдельный том `qadam-local_postgres_data`, поэтому данные
первой Docker-подготовки сохраняются. Секретный локальный файл также сохраняется;
его значения не попадают в вывод или сборку. Подробности локального входа —
в [LOCAL_DOCKER.md](LOCAL_DOCKER.md).

`docker:check` проверяет отдельное API через HTTP и SQL, затем перезапускает
PostgreSQL, API и интерфейс и проверяет тот же заказ повторно.

Остановить с сохранением данных:

```powershell
npm run docker:down
```

## Сборка и настройки

- `npm run build` собирает прежнее приложение и самостоятельный API.
- `npm run build:backend` собирает только API; `npm run start:backend` запускает
  его на порту 3102. Для запуска нужны серверные настройки окружения, поэтому
  для обычной локальной работы проще использовать готовый Docker.
- `npm run build:frontend` собирает только интерфейс; `npm run start:frontend`
  запускает его на порту 3103. До сборки задаётся `NEXT_PUBLIC_API_ORIGIN`; локальный
  адрес по умолчанию — `http://127.0.0.1:3102`, в Docker — порт 3210.
- `NEXT_PUBLIC_API_ORIGIN` — публичный адрес без паролей, пути, query и fragment.
  На публичном размещении нужен HTTPS; HTTP разрешён только для loopback-адресов.
  Адрес включается в клиентскую сборку, при его изменении интерфейс пересобирается.
- Обёртка `scripts/apps.mjs` не передаёт серверные секреты в отдельные сборки и
  процесс интерфейса. У фронтенда нет `DATABASE_URL`, токена бота, секрета вебхука
  или ключа карт. Новая конфигурация фронтенда также явно отвергает эти значения.
- У API: `QADAM_BACKEND=true`, `APP_ORIGIN` — точный адрес **интерфейса**,
  `API_ORIGIN` — точный адрес API, `DATABASE_URL` — серверное подключение к БД.
  Режимы `DEMO_AUTH_ENABLED` и `TELEGRAM_AUTH_ENABLED` задаются явно.
- `QADAM_LOCAL_DOCKER=true` по-прежнему ограничен частным `db:5432` и локальными
  адресами. Это не готовый режим доступа к публичной БД. Перед VPS потребуются
  отдельная серверная роль, HTTPS и резервное копирование с проверкой восстановления.
- Новые подпроекты имеют общий корень трассировки зависимостей. Локальные файлы
  сборки и копия `frontend/public/` игнорируются Git и Docker-контекстом.

## Сессии, CORS и карта

Telegram-сессия передаётся как Bearer-токен и хранится только в памяти страницы.
Запросы с ней отправляются без cookies, в том числе загрузка защищённых фрагментов
карты. Браузерный вход в локальном окружении использует HttpOnly-cookie.

API разрешает браузеру обращаться с точного `APP_ORIGIN`; у локального адреса
есть алиас `localhost`/`127.0.0.1` с тем же протоколом и портом. Другие источники,
неподдерживаемые методы и посторонние заголовки предварительного запроса отвергаются.
Wildcard не используется. CORS не заменяет авторизацию: каждый обработчик
по-прежнему проверяет сессию, роль и принадлежность заказа.

## Постоянная очередь Telegram

В самостоятельном API очередь из PostgreSQL обрабатывается постоянным worker,
запускаемым при старте Node.js-сервера. Он выполняет по одной партии, повторяет
попытку после ошибки и при перезапуске продолжает задачи из той же БД. Сохраняются
существующие блокировки, дедупликация и расписание повторных попыток в SQL.

Маршруты в этом режиме сохраняют задачу и быстро отвечают; `waitUntil` используется
только прежним размещением на Vercel. При остановке worker прекращает брать
новые партии и ожидает текущую. Доставка Telegram, как и прежде, не гарантирует
строго однократную отправку при сбое между запросом Telegram и записью результата.

В локальном Docker реальные токены отсутствуют и Telegram-вход выключен, поэтому
worker не отправляет настоящих сообщений. Браузерные тесты используют синтетическую
подпись Telegram и отдельную `_test` БД; worker у них отключён локальным флагом
`TELEGRAM_WORKER_ENABLED=false`. Для публичных адресов такое отключение запрещено,
если Telegram включён. Реальный бот проверяется на этапе размещения.

## Проверки

Обязательный набор:

```powershell
npm run typecheck
npm test
npm run build
npm run check:build
npm run test:e2e
npm run docker:up
npm run docker:check
```

`test:e2e` включает прежние сценарии, затем собирает отдельный интерфейс и проверяет
его с отдельным API на портах 3103/3102: CORS, авторизацию, лимит тела, создание и
завершение доставки, повторное открытие и восстановление после недоступности API.
`check:build` проверяет серверные зависимости всех прежних и отдельных API-маршрутов.
Результат 27.10.2026: все проверки прошли. Typecheck, 68 серверных тестов,
сборка прежнего приложения и API, отдельная сборка фронтенда, проверка состава
20 прежних и 20 отдельных API, 28 прежних браузерных сценариев и 3 сценария
с отдельным API. Итоговая команда `npm run test:e2e` выполнена полностью и успешно.
Три Docker-контейнера healthy; синтетический заказ доступен после перезапуска
БД, API и интерфейса. В runtime-контейнере фронтенда проверены отсутствие
серверных секретов и API-маршрутов, запуск без root; интерфейс открыт в браузере.
Новые SQL-миграции не понадобились, существующие файлы миграций не менялись.
