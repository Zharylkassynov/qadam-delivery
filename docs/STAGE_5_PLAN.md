# Этап 5: план цены, оплаты и связи

28.10.2026. Ветка `stage-5-pricing-contacts`.
**Сейчас выполнено только исследование и планирование.** Реализация, миграции,
подключение нового поставщика и публикация не начаты. План ниже ждёт утверждения
владельца по пункту 3.1 [ROADMAP](ROADMAP.md).

Решение владельца: комиссия сервиса пока **0%**. Для нового заказа с ценой
`platform_fee_kzt = 0`, `courier_payout_kzt = price_kzt`. Не вводим сбор
клиенту под другим названием. Расходы инфраструктуры несёт команда.

## 1. Порядок работ и условия начала

1. **Исследование и правила тарифа.** [Результат публичного исследования](pricing-research.md)
   и [шаблон замеров](pricing-observations.md) подготовлены. Команда выбирает
   пилотный транспорт/зону/посылку, проверяет реальные предложения и расходы
   курьеров. Точные ставки ещё не утверждены; иллюстрации не являются тарифом.
2. **Проверка источника пробок.** После утверждения плана — отдельная техническая
   проверка TomTom на бесплатном аккаунте: 10 пар адресов, направления, текущее
   и свободное время, класс транспорта, ошибки/лимиты, правила хранения и
   отображения. Аккаунт и принятие условий — владелец. Ключ не присылать в чат.
   Если качество/условия не подходят, обсуждаем 2ГИС/Яндекс или честную модель
   без актуальных пробок; платный сервис автоматически не подключаем.
3. **Макет.** Состояния цены, подтверждения номера и контактов. Использовать
   `frontend-design` и Figma; альтернативный локальный макет — с отдельным
   согласованием, если лимит Figma остаётся исчерпанным. Владелец утверждает
   экраны и изменённые тексты правил/политики до реализации.
4. **Реализация.** Серверная цена, безопасные предложения, снимок цены заказа,
   способы оплаты и контакты, оба варианта API, тесты и локальный Docker.
5. **Публикация.** После всех проверок — воспроизводимая миграция, проверка прав
   Production-соединения, ручной push/PR/merge владельца и проверка Vercel.
   Затем два Telegram-аккаунта и небольшой добровольный пилот.

Старый план этапов сохраняется. Этап 5 уточняется этим исследованием; этапы
6 и далее не начинаются. Инфраструктура пока Vercel + существующий PostgreSQL;
аренда сервера и перенос в Казахстан остаются отдельным согласованием.

## 2. Поведение приложения

1. Клиент выбирает адреса/точки и поддержанный класс посылки/транспорта.
2. API получает дорожные км и расчётное время, применяет утверждённую версию
   тарифа. Клиентские расстояния, минуты и суммы не являются доверенными.
3. Экран подтверждения показывает полный итог, кто платит, способ расчёта,
   источник/качество оценки и срок действия предложения. При изменении точек,
   транспорта или платных параметров старое предложение сбрасывается.
4. На подтверждении API атомарно связывает предложение с заказом и сохраняет
   сумму. Просроченное или изменённое предложение требует нового подтверждения;
   автоматического согласия с более высокой ценой нет.
5. До принятия курьер видит всю выплату, дорожную дистанцию, расчётное время,
   способ оплаты и плательщика. Принять может только подходящий класс курьера.
6. После назначения стороны видят разрешённые телефоны и кнопки звонка.
   Весь итог доставки причитается курьеру; цена не меняется в пути.

Наличные и перевод Kaspi — способы прямого расчёта с курьером. Выбор
`KASPI_TRANSFER` сам по себе не подтверждает поступление денег. В этапе 5
не будет банковского API, автосписания, хранения карты, оплаченного эскроу
или фиктивной отметки «Оплачено» на основании выбранного способа.

## 4. Предложение цены и надёжность

- Предложение привязано к пользователю, точным точкам, транспортному классу,
  параметрам посылки/услуг и версии тарифа. Поле `quote_id` не является
  разрешением использовать чужую цену.
- Дорожное расстояние и время получены для одного маршрута одного профиля.
  Рендер дороги и расчёт должны согласовываться после проверки лицензии.
- Учитываем ожидаемое начало дороги после подачи/получения. Прогноз не выдаётся
  за наблюдение будущих пробок. Модель пилота относится к одиночной доставке;
  ограничение одним активным заказом на курьера согласуем отдельно, до включения
  такого режима. Оптимизация совместного развоза в этот расчёт не входит.
- Примерный срок действия — до 5 минут от данных маршрута; точный TTL согласуем
  после проверки поставщика. Кэш текущего трафика — короткий, ориентир 1–2 минуты
  и только если разрешён условиями. Суточный кэш старой дорожной геометрии
  не подходит для текущего трафика. Время получения не выдаём за время сенсора.
- Новые вызовы только при изменении расчётных параметров/явном повторе.
  GPS курьера, опрос заказа и каждый символ адреса не вызывают расчёт цены.
- Никаких сетевых запросов провайдеру внутри долгой SQL-транзакции.
  Утверждённое предложение сохраняется до создания, затем короткая транзакция
  проверяет его и создаёт заказ с блокировкой от повторного использования.
- Повтор прежнего `request_key` возвращает уже созданный заказ с прежней ценой,
  даже если предложение успело истечь. Одновременное создание не создаёт
  два заказа по одному предложению.
- Нет подтверждённого маршрута/текущего времени — понятный отказ новой
  фиксированной цены с повтором или согласованием. Резервный автоматический
  тариф включается только после отдельного утверждения. Сохранённые заказы
  продолжают открываться и завершаться без доступного провайдера.
- Внешнему сервису передаются только необходимые точки/профиль маршрута,
  не телефоны, Telegram ID, имена или содержимое посылки. В логах не должно
  быть ключей, полных URL с ключами и контактов. Политика раскрывает нового
  поставщика и возможную внешнюю обработку точек: переезд БД в Казахстан
  сам по себе не локализует внешние запросы карт.

## 5. Миграции (проект схемы, SQL ещё не создавался)

Новые миграции, без редактирования применённых файлов:

- `qadam.order_quotes`: владелец, привязанные параметры, версия тарифа,
  денежные составляющие, источник маршрута/качество трафика, сроки,
  признак использования. Ровно необходимые индексы по владельцу/сроку
  и ограничение повторного использования. Геометрию и сырой ответ провайдера
  не хранить бессрочно; состав и срок хранения его производных зависят
  от подтверждённых условий поставщика.
- `qadam.orders`: `price_kzt`, `courier_payout_kzt`, `platform_fee_kzt`,
  `distance_m`, расчётные секунды, `price_source`, `traffic_source`, версия
  тарифа/разложение суммы, `payer`, `payment_method`, класс транспорта и
  ссылка на использованное предложение. Цена — снимок собственных условий
  сделки; доступность хранения внешних расчётных метрик проверить отдельно.
- `qadam.user_profiles`: номер, способ и время подтверждения, `phone_verified`,
  время обновления. Номер из ручной анкеты не становится подтверждённым
  автоматически. `requestContact` с результатом `true` в браузере сам по себе
  также не является серверным доказательством номера.
- Ограничения неотрицательных целых сумм, соответствие выплаты цене и нулевая
  комиссия для новых цен этого этапа. Старые заказы с неизвестной ценой
  остаются без цены; ноль не означает неизвестную сумму. Не присваивать им
  новый тариф задним числом.
- Приватная схема, RLS, отзыв доступа у публичных ролей и ровно необходимые
  права `qadam_app`. Проверка владельца предложения/заказа в API обязательна:
  общая серверная роль сама по себе не изолирует пользователей приложения.
- Файл миграции, SHA-256 и запись `public.qadam_migrations`; готовый SQL
  в `docs/sql/`. Сначала локальная PostgreSQL и существующие данные, затем
  Supabase и проверка реальной ограниченной роли до выкладки нового кода.

## 6. Проверки реализации

- Цена меняется от км/минут предсказуемо, минимум и округление корректны,
  двойной платы за пробки нет, комиссия равна нулю, выплата равна итогу.
- Подмена цены/расстояния/версии тарифа, чужое/просроченное предложение,
  изменение класса/точек, повтор и одновременное создание.
- Подтверждённые контакты привязаны к отправителю Telegram-вебхука;
  чужой контакт не подтверждает профиль. Телефоны не видны неназначенным
  курьерам/чужим клиентам/публичной карте.
- Несоответствующий транспорт не принимает заказ, для которого не подходит.
- Таймаут/ошибка/429 поставщика, отсутствие полей трафика, неверная геометрия,
  неподдержанная зона. Запрошенная модель не считается полученными данными
  без проверки ответа. Старая доставка работает при недоступной цене.
- Сохранение суммы и параметров после изменения тарифа, перезагрузки страницы
  и перезапуска Docker. Исторические заказы без цены остаются читаемыми.
- Браузер: создание → подтверждение цены → принятие → звонок → завершение,
  истечение предложения и новые условия только с явным подтверждением,
  мобильные размеры, доступность и все состояния утверждённого макета.
- Сборка общего приложения и отдельного API/фронтенда, запрет утечки ключа
  и трассировка сертификата новых маршрутов. Пять обязательных команд:
  `npm run typecheck`, `npm test`, `npm run build`, `npm run check:build`,
  `npm run test:e2e`.

## 7. Ручные действия владельца/команды

1. Утвердить этот план, пилотный класс и зону. По возможности завершить GPS-проверку
   этапа 4.1 на двух реальных телефонах; её результат пока не подтверждён.
2. Выбрать владельца аккаунта карт, получить бесплатный доступ, проверить условия.
   Секрет вводится владельцем в защищённые настройки, не публикуется в чате/Git.
3. Разделить 10 пар адресов между пятью участниками и заполнить замеры без
   оформления фиктивных доставок. Обсудить расходы с потенциальными курьерами.
4. По результатам утвердить тариф и макет. Ни один пример из исследования
   автоматически не превращается в рабочую цену.
5. После реализации — проверить расчёт, номер Telegram и звонки двумя аккаунтами;
   при публикации вручную commit/push/PR/merge. Бот-команды с токеном выполняет
   только владелец. Ассистент проверяет согласованные Vercel/Supabase задачи.
6. Провести добровольный пилот и решить, какие ставки/профили корректировать.

Для текущего исследования изменены только документы. Пять команд реализации
для документации не запускались; перед сдачей кода этапа они обязательны.
