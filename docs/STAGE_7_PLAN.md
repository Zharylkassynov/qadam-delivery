# Этап 7 — подтверждение вручения и управление доставками

31.10.2026. Ветка `stage-7-delivery-trust`.
Владелец утвердил начало этапа, локальный макет вместо Figma и дополнения правил/политики.
31.10 отдельно утверждено уточнение: доступ к фото в Qadam 30 суток, автоудаление
сообщения в служебном канале Telegram — месяц (31 сутки). Реализация подготовлена;
результаты проверки и публикации фиксируются в [инструкции](STAGE_7.md) и ROADMAP.
Автоматическая цена остаётся выключенной.

## Порядок работы

1. Проверить существующие сценарии и ограничения Telegram.
2. Подготовить макет и тексты, показать владельцу и получить утверждение.
3. Реализовать согласованные сценарии, миграцию и отдельный API.
4. Выполнить обязательные проверки, обновить статус и дать текст коммита.
5. Владелец публикует код через GitHub и проверяет Telegram на телефонах.

## Фото вручения

- Для новых заказов после подключения сервиса фото требуется при завершении.
  У существующих заказов требования не меняются задним числом: сохраняется снимок
  `photo_required` и `code_required` на момент создания.
- «Завершить доставку» открывает отдельный экран: фото, при необходимости код,
  подтверждение фактической передачи. Статус меняется только после сохранения
  обязательных сведений. Обычный POST статуса не обходит проверку.
- Кнопки «Снять фото» и «Выбрать фото». Открытие камеры зависит от устройства;
  фотография не считается техническим доказательством съёмки в реальном времени.
- Клиент сжимает изображение; сервер проверяет и перекодирует его, удаляет EXIF.
  Итоговый JPEG не больше 1 МиБ, длинная сторона не больше 1600 px. Невалидные,
  чрезмерно большие и повреждённые файлы отклоняются до отправки провайдеру.
- Фото доступно только владельцу заказа, действующему назначенному курьеру и
  администратору. Доступ проверяется и для бинарного ответа. Серверный прокси
  не раскрывает токен, Telegram URL, канал и `file_id`; ответ `no-store`.
- Служебный приватный канал Telegram — только бот и необходимые администраторы.
  В подписи — номер заказа без телефонов, адресов и текста открытки. Метаданные
  фото хранятся в PostgreSQL. После успешного завершения клиент получает фото
  через бота, если разрешены сообщения; сбой уведомления не отменяет доставку.
- Для Qadam утверждён срок доступа 30 суток от загрузки. В служебном канале
  владелец включает автоудаление на один месяц (31 сутки); готовность проверяется через
  `getChat.message_auto_delete_time`. После истечения API не выдаёт фото, запись
  помечается истёкшей, ссылка на файл очищается обслуживающей процедурой.
- Удаление сообщения не означает гарантированное физическое удаление всех копий
  файла у Telegram. Ранее полученные сообщения/сохранённые копии у клиента могут
  остаться. Обращения об удалении обрабатывает Команда Qadam вручную; старые
  сообщения служебного канала при необходимости удаляет его администратор.
- После смены курьера ранее загруженный им снимок не подтверждает новую передачу.
  История попыток сохраняется для администратора, новому курьеру нужен свой кадр.
- При ошибке загрузки показывается повтор. Нельзя сообщать «Доставлено», пока
  обязательное подтверждение не сохранено. Сбой просмотра старого фото не ломает
  историю заказа. Нет бесконечного хранения снимков или скрытого обхода проверки.

### Ограничения провайдера

Проверено 31.10 по первичным источникам:

- [Telegram Bot API: sendPhoto](https://core.telegram.org/bots/api#sendphoto)
  принимает фото до 10 МБ; собственный лимит Qadam меньше.
- [getFile](https://core.telegram.org/bots/api#getfile) выдаёт путь загрузки с
  токеном бота; этот путь остаётся только на сервере.
- [deleteMessage](https://core.telegram.org/bots/api#deletemessage) ограничивает
  удаление ботом сообщениями моложе 48 часов. Поэтому нельзя обещать фоновое
  удаление старых фото одним вызовом бота.
- [Telegram: автоудаление](https://telegram.org/blog/protected-content-delete-by-date-and-more)
  поддерживает срок в месяц. Это отдельная настройка владельца канала; таймер
  проверяется перед включением функции, физическое стирание всех копий не обещается.

## Код вручения

- Отправитель включает «Код при вручении» до создания заказа; исходно он выключен. Четыре случайные
  цифры, включая ведущие нули. Код виден только отправителю в отдельном ответе;
  он передаёт его получателю и просит назвать после получения посылки.
- Код не отправляется автоматически на телефон получателя, не попадает в
  рассылки, общий JSON заказа, логи или интерфейс администратора/курьера.
- В БД — проверочное значение с серверным секретом и зашифрованная копия для
  повторного просмотра отправителем. Секрет отдельный, только серверный;
  отсутствие конфигурации не должно делать код фиктивно успешным.
- Завершает текущий назначенный курьер в `IN_TRANSIT`, с сохранённым фото, если
  оно обязательно, и корректным кодом. Проверка и завершение — одна транзакция.
- Максимум пять неправильных попыток на версию кода. Счётчик сохраняется даже
  при ошибочном ответе; обновление страницы и одновременные запросы его не сбрасывают.
  Повтор того же запроса не расходует попытку дважды.
- Если код потерян, отправитель может посмотреть его или выпустить новый;
  перевыпуск ограничен по частоте и количеству. После исчерпания попыток — новый
  код отправителя или помощь администратора с обязательной причиной в истории.
  Старый код после перевыпуска/смены курьера не действует. Подтверждённый заказ
  повторно завершать и сбрасывать нельзя; ручного обхода кода нет.
- Повтор старого заказа не переносит код и признак его включения без нового выбора.

## Отказ и административное управление

- Назначенный курьер может отказаться только в `ACCEPTED`, до получения посылки.
  Нужна причина 5–500 символов. Заказ возвращается в поиск, старый курьер теряет
  доступ к контактам/открытке и передаче координат этого заказа. Очищаются текущие
  номер курьера и GPS назначения, клиент получает уведомление, очередь обновляется.
- Администратор назначает или меняет одобренного активного курьера, отменяет
  незавершённый заказ, блокирует и разблокирует курьерский доступ. Причина 5–500
  символов обязательна. Ограничения транспорта/контакта и одного активного
  фиксированного заказа сохраняются, сумма заказа не меняется.
- После забора нельзя просто вернуть посылку в общую очередь. Смена курьера
  требует подтверждения администратором согласованной физической передачи;
  отмена — подтверждения согласованного местонахождения/возврата посылки.
- Блокировка прекращает курьерские операции и GPS, исключает из свободной карты,
  рассылок и нового назначения. Одобренная заявка остаётся в истории. Личный
  клиентский аккаунт сохраняется. Активные заказы не исчезают и не становятся
  свободными автоматически: администратор отдельно организует их передачу/отмену.
- Изменения выполняются с проверкой ожидаемого статуса и назначения: устаревший
  экран получает конфликт и обновление, а не перезаписывает чужое решение.
- Транзакции, стабильные блокировки назначений и ключи повторных запросов
  защищают от гонок. Побочные уведомления — через существующую очередь.
- История хранит вид действия, исполнителя, время, прежнее/новое назначение и
  причину. В обычных ответах скрываются служебные примечания; участнику доступны
  относящиеся к его доставке объяснения без чужих персональных сведений.
- Отмена в Qadam не возвращает автоматически наличные или перевод Kaspi.

## Оценка

- Владелец завершённого заказа может один раз отправить 1–5 и комментарий до
  500 символов. Оценка привязана к заказу, повторы безопасны.
- Отправитель видит собственный результат. Администратор видит его в заказе;
  курьер и другие клиенты не получают оценку или комментарий, публичного рейтинга нет.
- Для исправления отправленного отзыва — существующий контакт команды.

## Включение и ручные шаги

- До настройки подтверждение фото/кода выключено; остальные согласованные
  возможности этапа можно проверять отдельно. Новые требования включаются
  только после готовности служебного канала, серверного ключа, текстов и проверки.
- Владелец создаёт приватный канал, добавляет бота администратором с правом
  публикации и включает автоудаление на один месяц (31 сутки). Канал не предназначен для клиентов.
  Команда `npm run telegram:storage:check` проверяет канал без смены вебхука.
- Согласованные настройки Vercel/Supabase выполняет ассистент. Команды с токеном
  Telegram запускает владелец; `.env*` и `.secrets` с секретами не читаются/не выводятся.
- После реализации владелец делает commit/push/PR/merge и проверяет два аккаунта
  на телефонах: фото, неверный/верный код, отказ и повторное назначение, оценку.
  Проверяется также iPhone: камера/галерея, отмена выбора, повтор при потере сети.
- Подключение PS.kz, активация автотарифа и платные подписки не входят в этап.

## Проверки перед сдачей реализации

Все пять: `npm run typecheck`, `npm test`, `npm run build`,
`npm run check:build`, `npm run test:e2e`.

Отдельно: чужое фото/код, поддельный MIME/EXIF, лимиты загрузки, старая сессия
заблокированного курьера, старый курьер после смены, неверные/параллельные попытки
кода, обход через POST статуса, повтор после потерянного ответа, гонки назначений,
сохранение фиксированной цены, ошибки Telegram и приватность оценки. Браузерные
проверки используют синтетические аккаунты и подмену провайдера, не отправляют
реальные фото третьим лицам. Реальные телефоны проверяются после публикации.
