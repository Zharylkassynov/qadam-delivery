# Этап 4: заказы и уведомления

Ветка `stage-4-order-notifications`. Владелец разрешил этап и утвердил локальный
макет [переключателя курьера](design/stage-4.html) вместо Figma после исчерпания
лимита Starter. Покупка сервера и перенос Production сюда не входят.

## Поведение

- Одобренный курьер включает «Я на линии» над доступными заказами. Состояние
  сохраняется на сервере и действует 8 часов с последнего включения. Ошибка
  сохранения оставляет последнее подтверждённое состояние; есть повтор запроса.
- Новый заказ создаёт задания на отправку в той же транзакции, что и заказ.
  После сохранения бот отправляет их активным курьерам на линии, разрешившим
  сообщения. Перед отправкой отложенного задания эти условия проверяются снова.
- Сообщение содержит адреса и расстояние по прямой между сохранёнными точками.
  Если точек нет, расстояние предлагается уточнить в приложении. Имя, телефон
  получателя и комментарий не отправляются в рассылку.
- После принятия или отмены ранее отправленные сообщения остальным курьерам
  закрываются; кнопка убирается. Сохраняется `message_id`, в том числе при принятии
  заказа во время отправки сообщения. Открывший старую ссылку курьер проходит
  повторную проверку доступа на сервере.
- Клиенту с разрешением на сообщения приходят назначение курьера, получение
  посылки, начало доставки, завершение и отмена. Повтор запроса не дублирует
  задания; задержка Telegram не меняет порядок статусов одного заказа.
- Заказ без курьера старше 10 минут вызывает одно оповещение доступным админам
  при запросе обычного или административного списка. Отдельного расписания нет:
  если никто не запрашивает списки, проверка ждёт следующего открытия приложения.
- Ссылки `/?order=<uuid>` и подписанный `startapp=order_<номер>` открывают заказ.
  Администратору сообщение ведёт в наблюдение за заказом. Права проверяются при
  каждом запросе; чужой завершённый заказ недоступен обычному курьеру.
- Список обновляется раз в 15 секунд, открытый заказ — раз в 3 секунды, пока
  приложение видно. Режим на линии управляет сообщениями и не включает фоновую
  геопозицию при закрытом Mini App.

## База и отправка

Миграция: `db/migrations/20261027173430_order_notifications.sql`.
Для SQL Editor сохранён [готовый SQL](sql/stage-4-order-notifications.sql), включая
запись контрольной суммы в `public.qadam_migrations`. Выполнять один раз.
Новые таблицы закрыты от клиентских ролей, включён RLS; права имеет `qadam_app`.
Существующие данные сохраняются. Миграция должна быть применена **до публикации кода**.

27.10.2026 миграция применена ассистентом в Supabase проекта Qadam Delivery.
Контрольная сумма, RLS, права `qadam_app` и отсутствие доступа клиентских ролей
проверены. Повторно выполнять SQL владельцу не нужно.
SHA-256: `5086c548ee78881e87fdcbf65cfb1f18ae7f4cceb3c4af6cb9d426918ab9219b`.
Повторить проверку прав без изменения данных: `npm run db:cloud:transaction:check`.

На Vercel отправка запускается через `waitUntil` после запросов и вебхука. Повторы
сохраняются в базе; отложенные задания подхватываются при следующем запросе.
В отдельном API работает постоянный worker, который продолжает очередь после
перезапуска. Доставка Telegram выполняется с повторами; при неопределённом сетевом
ответе Telegram теоретически может принять сообщение до повторной отправки.

Новых секретов не требуется. `TELEGRAM_WORKER_ENABLED=false` применяется только
в локальных браузерных тестах, чтобы они не отправляли сообщения в настоящий бот.
В публичном приложении с включённым Telegram отключение worker запрещено проверкой
настроек. Docker без Telegram позволяет проверить переключатель и заказы; для
реальных сообщений нужен опубликованный бот.

## После проверки кода владельцем

1. Закоммитить изменения, отправить ветку и открыть PR в GitHub. Дождаться зелёного
   CI, затем объединить PR. Vercel автоматически опубликует `main`.
2. Если вебхук этапа 2 ещё не подключён, самостоятельно выполнить:

   ```powershell
   npm run telegram:check
   npm run telegram:webhook
   ```

   Команды читают локальные настройки сами. Секреты в чат не отправлять.
3. На двух аккаунтах Telegram отправить `/start` боту. Курьер должен быть одобрен
   администратором; включить «Я на линии» и разрешить сообщения.
4. Клиент создаёт доставку: курьер получает адреса и кнопку заказа. Для проверки
   закрытия сообщения можно включить второго одобренного курьера.
5. Курьер принимает заказ: сообщение второго курьера меняется на «Заказ уже
   принят», клиент получает имя назначенного курьера.
6. Курьер последовательно отмечает получение, начало доставки и завершение;
   клиент получает три сообщения. Кнопки открывают соответствующий заказ.
7. Проверить отмену нового заказа и оповещение админа: оставить другой заказ без
   курьера дольше 10 минут, затем открыть список. Повторное обновление списка
   не должно создавать второе оповещение по этому заказу.

Короткий текст коммита: `Add order notifications and courier availability`.

`npm run build` (прежнее приложение и отдельный API), `npm run check:build`
(22 + 22 API-маршрута) и `npm run test:e2e` (30 сценариев прежнего приложения

`npm run docker:up` применил десятую миграцию в отдельной локальной базе;
все три контейнера здоровы. `npm run docker:check` подтвердил вход и тот же
заказ после перезапуска PostgreSQL, API и интерфейса. Сообщения Telegram
проверены с подменённым транспортом: фильтрация курьеров, истечение смены,
дубли запросов, конкурирующее принятие, отправка в момент принятия, порядок
статусов при 429, отказ 403 и атомарное оповещение о долгом ожидании.
Браузерные проверки охватывают ширины 320, 360, 390 и 1440 px, ошибку и повтор
сохранения, разрешение сообщений, сохранение после перезагрузки и доступ по ссылкам.
