# Локальная подготовка к переносу бэкенда

Дата: 27.10.2026. Ветка: `stage-2-local-docker`.

## Что подготовлено

Существующее приложение Next.js и PostgreSQL 17 запускаются в отдельных контейнерах.
Это первый подготовительный шаг перед схемой «фронтенд на Vercel, API и БД на PS.kz».
Сейчас контейнер приложения содержит и существующие API, и интерфейс: самостоятельное
API и прямое подключение фронтенда к нему будут следующим согласуемым шагом.

Новая инфраструктура пока локальная. Vercel, Supabase, Telegram и их действующие
адреса этим шагом не переключаются. Аренда сервера не нужна.

## Запуск

Нужны Docker Desktop с Linux-контейнерами и Node.js 22. Запустить Docker Desktop,
затем из папки проекта:

```powershell
npm run docker:up
npm run docker:check
npm run docker:status
```

Первый запуск скачивает официальные образы, устанавливает зависимости из lock-файла
и собирает приложение. Следующие сборки используют кеш Docker.

Открыть <http://127.0.0.1:3200>. Это локальная версия с браузерным входом.
Есть `customer1..3@qadam.demo` и `courier1..3@qadam.demo`; скрипт автоматически
создаёт случайные пароли только для локального окружения. Для ручного входа владелец
может самостоятельно посмотреть `QADAM_DOCKER_DEMO_PASSWORD` в
`.secrets/docker-local.env`. Ассистент значения не читает и не выводит.

`docker:check` сам входит в локальный аккаунт, создаёт один синтетический заказ,
проверяет его через API и SQL, перезапускает **базу и приложение** и снова проверяет
вход и доступность того же заказа. Повторные проверки используют тот же ключ запроса
и не создают новые заказы. Проверка работает только с БД `qadam_docker` внутри Compose.

Остановка с сохранением данных:

```powershell
npm run docker:down
```

Для просмотра последних сообщений приложения:

```powershell
node scripts/docker-local.mjs logs
```

## Изоляция и данные

- `compose.local.yaml` использует собственный проект `qadam-local`, БД `qadam_docker`
  и постоянный том `qadam-local_postgres_data`. Обычный `compose.yaml` и его БД
  для разработки и тестов остаются отдельными.
- Приложение доступно только на `127.0.0.1:3200`. Порт PostgreSQL на компьютер
  и в интернет не публикуется.
- При запуске применяются существующие миграции; проверяются их сохранённые SHA-256.
  Применённые SQL-файлы не меняются. Затем создаются локальные аккаунты.
- `.secrets/docker-local.env` создаётся один раз и не перезаписывается при повторном
  запуске. Файл игнорируется Git. Не удалять его, пока нужен существующий том БД.
- Контекст сборки Docker содержит только разрешённые исходники. `.env*`, `.secrets`,
  Git, локальные зависимости и отчёты в образ не попадают. Секреты не передаются в сборку.
- Обычные команды остановки и проверки сохраняют том. Том сохраняет данные при
  перезапуске, но **не заменяет резервную копию**.
- Образы приложения и инструментов запускаются пользователем `node` без root.
  Миграции и TypeScript-инструменты находятся в отдельном образе `tools`.
- Флаг `QADAM_LOCAL_DOCKER=true` разрешает соединение без TLS только с `db:5432`
  без дополнительных параметров URL. В Vercel этот режим запрещён. Проверка TLS
  для облачных подключений сохраняется.
- Реальные токены Telegram и Geoapify в локальные контейнеры не передаются. Этот
  шаг проверяет локальное API и сохранность данных; настоящие сообщения Telegram,
  геокодинг и перенос существующих данных проверяются на следующих шагах.
- Локальная БД использует владельца для подготовки и проверки. Перед публичным
  размещением нужна отдельная ограниченная серверная роль, HTTPS, резервные копии
  и проверка восстановления. Этот Compose нельзя считать готовой конфигурацией VPS.

## Что дальше

После обсуждения команды подготовить отдельный план следующего шага:

1. Выделить API в самостоятельно запускаемый сервис, сохранив бизнес-логику.
2. Подключить интерфейс к отдельному API: адрес сервера, Telegram-сессии, строгий
   список разрешённых источников, запросы карты и обработка недоступности сервера.
3. Адаптировать очередь уведомлений к постоянному процессу вместо зависимости
   от Vercel `waitUntil`. Проверить повторные попытки после перезапуска.
4. Подготовить размещение API и PostgreSQL на PS.kz: HTTPS, права, секреты,
   копии вне VPS и восстановление. Фронтенд оставить на Vercel.
5. Выполнить пробный и финальный перенос данных, проверить переключение и откат.
6. Продолжить функциональные этапы дорожной карты на новой инфраструктуре.

Перед каждым следующим шагом — отдельный план и разрешение владельца.
GitHub остаётся за владельцем, команды с токеном Telegram он запускает сам.

## Проверки этого шага

27.10.2026 выполнены: typecheck, 62 серверных теста, сборка Windows, проверка
состава всех 20 API, 28 браузерных сценариев (2,6 минуты), сборка Linux-образов
и Docker-проверка заказа после перезапуска БД и приложения. Все проверки успешны.
В отдельной БД применены все 9 существующих миграций. Интерфейс из контейнера
открыт в браузере: оформление и локальные шрифты загружаются. Проверены запуск
приложения без root и отсутствие `.env*`, `.secrets` и Git в runtime-образе.
Секретный локальный файл игнорируется Git; порт БД не опубликован на компьютере.

Команды для воспроизведения:

```powershell
npm run typecheck
npm run db:test:setup
npm test
npm run build
npm run check:build
npm run test:e2e
npm run docker:up
npm run docker:check
```

Обычные проверки используют существующую отдельную тестовую БД из локального
окружения, Docker-проверка — только `qadam_docker`.
